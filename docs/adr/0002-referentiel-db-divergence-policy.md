# Divergence handling policy: strict on write, fallback on read, transitional only

`REFERENTIEL` and the `Notion`/`Competence` tables are two unsynchronized parallel sources. 4 divergence points already tolerate one having an entry the other lacks, by defaulting a score to `0.5` or skipping with a bare `print` (`build_notion_data_with_scores`, `init_progressions_for_user`, `persist_score_update` in `session_generator.py`, and the `lacunaire_notion` lookup in `app.py`). We unify these under one policy for the migration's transitional period (tickets 2-5, before `REFERENTIEL` is removed in ticket 6): **write paths fail loudly** (`persist_score_update`, `init_progressions_for_user` — never silently drop a score) while **read paths keep a documented fallback** (`build_notion_data_with_scores` — don't break an in-progress student session over a data gap). This protects data integrity on writes while keeping the training flow resilient on reads. The policy is explicitly transitional: once `REFERENTIEL` is deleted in ticket 6, there is only one source left and this class of divergence disappears entirely.

**Out of scope**: cascading deletion of a `Competence` that still has `Progression` rows attached (RESTRICT vs cascade vs soft-delete). No application code path deletes a `Competence` today — only direct Adminer access can — so this is deferred to a separate future decision, not this migration.
